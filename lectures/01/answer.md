### 取り組んだ内容

AI ツール（Gemini および GitHub Copilot）を組み合わせて活用した。

1. **プロンプトの設計（Gemini の活用）**

   便利関数（`client.chats.create()`）を使わず、コンテキスト送信の仕組みを検証するため、`contents` 配列の手動管理を強制するプロンプトを Gemini と対話しながら設計した。実際に使用したプロンプトは下記。

   ````text
   app/ask.py を改修して、ターミナル上で連続して対話ができるCUIチャットツールを実装してください。

   【厳格な制約事項】
   ・`client.chats.create()` や `Chat` オブジェクトは絶対に禁止です。使わないでください。
   ・代わりに、`client.models.generate_content` を使用し、引数 `contents` に対話履歴のリストを渡す構成にしてください。

   【具体的な実装要件】
   1. 対話履歴を管理する空のリスト `contents = []` をループの外で定義してください。
   2. while ループを作成し、ユーザーから標準入力（input）で文字列を受け取ってください。ユーザーが `exit` または `quit` と入力したらループを抜けて終了してください。
   3. ユーザーの入力テキストを `types.Content(role="user", parts=[types.Part.from_text(text=user_input)])` として `contents` 配列に追加してください。
   4. `client.models.generate_content(model=..., contents=contents)` を呼び出してレスポンスを得てください。
   5. モデルの返答テキストを `types.Content(role="model", parts=[types.Part.from_text(text=response.text)])` として `contents` 配列に追加してください。
   6. レスポンスの直後に、入力トークン数（prompt_token_count）と出力トークン数（candidates_token_count）を表示する処理を入れてください。
   ````

2. **コード・テストの自動生成（GitHub Copilot の活用）**

   作成したプロンプトを GitHub Copilot に与え、`app/ask.py` の改修コードを作成させた。あわせて、必要な `pytest` 用のテストコードも GitHub Copilot に生成させた。

3. **コードのレビューと検証（人間による確認）**

   生成されたコードとテストコードを読み込み、意図通り `role="user"` / `role="model"` が交互に `contents` へ追加されていること、および `pytest` がすべて通ることを手元で確認・採用した。

### 気づき・疑問

**気づき**

- トークン数は `ask.py` が数えているのではなく、Gemini API がレスポンスの `usage_metadata` に入れて返す値を表示している。数えているのは Google のサーバー側である。
- `prompt_token_count` は、その呼び出しで送った `contents` 全体のトークン数である。そのため「前ターンの入力 + 前ターンの返答の出力 + 今回の質問」にほぼ等しく、会話が長いほど毎回の入力が増える（実測: 5 → 54 → 94）。一方、`candidates_token_count` はそのターンの返答だけの値で、累積しない。
- 会話を続けるほど、毎回送るトークンが増える。無料枠のレート制限や料金への影響が気になる。

**疑問**

- `candidates_token_count` には思考（thinking）分が含まれないようだ。思考するモデルでは、請求上の出力はもっと多くなるのか。`thoughts_token_count` や `total_token_count` も表示すべきか。
- 会話が長くなったとき、古い履歴を削る・要約するなどの対策をどうするか。
- 送信前に入力トークンを知りたい場合、`count_tokens` を使えばよいか。
