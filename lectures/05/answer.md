- 今回の用途に採用したい方式と、その理由・比較条件の限界 :
  - 採用したい方式 : ベクトル検索 (通常RAG)、または Graph探索。
  - 理由：
    - ベクトル検索は入力トークン数 (3,027 tokens) と費用 ($0.001446 USD) が最も低く、処理時間 (2.75秒) も早くでコストパフォーマンスが良い。
    - 全文投入は正確だが、入力トークン数 (117,025 tokens) と費用 ($0.035600 USD) が約25〜38倍と高く、大規模資料では現実的ではない。
    - Tree探索は構造を正確にたどれるが、応答ターン数(5回)と待ち時間 (5.11秒)が増加するため、ピンポイントな質問回答にはオーバースペック。
  - 比較条件の限界 :
    - 全文投入と他方式で対象資料の範囲が異なる (全文投入は全9資料438ページ、他は第1〜3回214ページ)。
    - 今回の質問が、単一の章・隣接2ページ内 (p.51-52) で完結する限定的な問いのため、複数章にまたがる複雑な検索やTree/Graphの真価が発揮されにくい条件。

- 気づき・疑問：
  - 全文投入はコンテキスト長が十分であれば一括処理できて強力。費用と処理時間が大幅に増えるため、RAGによる高信号トークンの絞り込み(コンテキストエンジニアリング)の重要性がデータで確認できた。
  - Tree探索は探索ターン数が増えるためコストと時間はかかるが、質問者が全体構造のどこに何があるかを把握したい場合には有効な探索手法である。

## 宿題

- 取り組んだレベル：実装
- やったこと (変更したファイル・設定・処理、または設計した取得方法) :
  app/retrieval.py の search 関数を改修。ベクトル検索の上位ヒット結果に対し、同じ資料 (document_id) 内の前後1ページ (page - 1 および page + 1) の本文も自動取得して重複を除外した上でコンテキストへ追加する処理を実装した。
- 比較した質問と、固定した条件 (モデル・対象資料など) :
  - 質問：第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？
  - モデル： gemini-3.5-flash-lite
  - 対象資料：第1〜3回講義資料 (214ページ)
- 結果(変更前後の回答・根拠、--trace の出力、時間・トークン数・生成API推定費用など) :
  - 変更前：入力 3,027 tokens / 時間 2.75秒 / 費用 $0.001446 USD (p.52 中心の参照)
  - 変更後：入力 5,229 tokens / 時間 5.19秒 / 費用 $0.002114 USD(p.51, p.52 を含んだ参照)
  - ツールの返却結果に p.51 (PEFT全体の比較) および p.52 (LoRA/QLoRA詳細) の前後ページが揃って含まれることを --trace で確認した。
- 改善した例と、残る失敗・制約 :
  - 改善した例：スライドを跨いで連続している説明や背景情報 (例：p.51でのPEFT位置づけとp.52でのLoRA詳細) を一度にコンテキストへ取り込めるため、補足説明を含めた回答の網羅性が向上した。
  - 残る失敗・制約：単一ページだけで十分答えられる質問の場合、前後ページの取得によってコンテキスト量と入力トークン数 (約1.7倍)、処理時間が加増し、不要な情報 (ノイズ) を含んでしまうコスト面のトレードオフが生じる。
- 気づき・疑問：
  検索の適合率 (Precision) とコンテキストの網羅性 (Recall)はトレードオフの関係にあり、質問の複雑さやタイプに応じてウィンドウサイズ (前後ページの付加数) を動的に制御する仕組みの重要性を実感した。
